## Console and delivery semantics

- The admin-only console creates drafts and templates, estimates an audience, schedules or queues campaigns, displays their status and per-device operational outcomes, cancels remaining work, and retries eligible discarded deliveries. Every write is authenticated, role-checked again in the database, rate-limited and audited. Queue/retry and release actions use request IDs to acknowledge an exact replay without applying it twice; a replay is a historical acknowledgment, not proof the current state is unchanged. After a lost response, retry the same action or wait and check the release and notification history before editing or beginning a different action. The console retains the request only while its section remains mounted; navigation or a reload loses that local reference. Selected shop/device lists are capped at 100; all-device audiences can be larger. Estimates are snapshots, not promises: eligibility is checked again at dispatch.
- Recipients of managed content must have explicitly opted in, remain members of the shop, and have registered with protocol v2. If delivery is separately enabled, older v1 installations can receive generic order/payment messages but cannot receive managed content. Registration reports the app's version and a random binding; the admin view does not expose FCM installation IDs. “Inactive” means no currently registered device for that shop has refreshed registration within 30 days; it is **not** proof that the app was unused. Version/adoption counts cover registered notification-enabled devices, not all installations. The worker eventually removes registrations not refreshed for 180 days.
- Managed content is plain title/body, an allowlisted in-app destination, and an optional public image from the approved path in this repository. Never put customer, order, payment, password or private data in an alert or image. Image retrieval is best-effort. The app checks its current opt-in and account binding before displaying and rechecks the original session and binding before a delayed tap navigates. The notification OS permission alone is not an FCM opt-in. The candidate maintenance gate, deployed only to isolated QA, exempts only the bearer-verified native opt-out DELETE and display-receipt POST, not registration or ordinary shop APIs; these exceptions are not yet end-to-end tested.
- A successful FCM request is **accepted**, not necessarily delivered or displayed. An optional authenticated, best-effort phone display receipt is separate and does not prove a person read the alert. A receipt can arrive before the worker records acceptance. Retries, crashes, phone settings, battery restrictions, offline phones, FCM and permission changes can still lose or duplicate alerts. A bounded local seen-event list and stable notification tags reduce duplicates, but are not an exactly-once guarantee. The order board and authoritative app data remain the source of truth.
- Enabled subscription announcements can automatically queue a notification. A linked promo must be enabled, within its window and not fully reserved at dispatch and immediately before the payload is read. Use neutral text: availability and offers can still change after a send starts. Maintenance enablement can queue a fixed notice. Editing a still-scheduled announcement updates its notice; disabling, expiring or editing a sending source stops remaining work where possible. A network request already in flight or accepted by FCM **cannot be recalled**. The authoritative announcement and maintenance setting are never rolled back just because enqueueing fails; check the audit trail for rate-limited actions and monitor worker errors.
- A shared database limit permits at most 10 campaign/retry queue actions per rolling hour and at most 120 claims per fixed 60-second window across both legacy and new worker RPCs (bursts can straddle window boundaries). Automatic notices can be skipped at the queue limit. These are safety ceilings, not promised throughput: the proposed scheduler runs every five minutes and a worker claims at most 30 deliveries per run. Large audiences may outlast the one-day event lifetime; load-test and size a separately approved scheduler before use.
- A scheduled campaign over one day late or past its source end time is cancelled. Outbox events are swept after seven days, so deleted events/devices cannot be retried. Durable campaign/audit and delivery-log rows currently have **no automatic retention purge**; agree on a privacy, capacity and archival policy before production. A log update failure cannot prevent opt-out, and can leave a stale pending log requiring operational investigation. Do not treat these counters as a legal delivery ledger.

## Managed release feed and installer

`PRINTLY_NATIVE_RELEASE_MANAGER_ENABLED=0` (or unset) leaves the authenticated shop download endpoint on its legacy environment-variable metadata and returns no managed policy to the native public feed. When enabled, the managed current release replaces that fallback; an explicit unpublish returns `available: false` and does not resurrect old environment metadata. A database error or invalid feed returns 503 rather than an unpublish; release notes and timestamps are checked against the Android parser's control-character, fractional-second and offset limits. A synthetic database test also checks that PostgreSQL's normalized release timestamp passes the server contract. Isolated QA does not receive the production APK policy.

An admin prepares a draft, then marks it published and selects one published version as current. Replacing or unpublishing a release cancels its unsent update notices where possible, and the worker rechecks that the release is still current; a network send already in flight cannot be recalled. Before publish/activation the server checks the exact repository's **public, non-draft, non-prerelease** GitHub asset and its reported SHA-256, and compares the entered public certificate fingerprint with the independently configured `PRINTLY_ANDROID_SIGNING_CERT_SHA256`. GitHub may omit a digest for older assets or rate-limit the API; in that case publication is refused. These server checks **do not independently inspect the APK's package, version or signer**. An admin must separately download the hosted bytes, run Android build tools and `apksigner`, compare the single signer against a trusted, independently obtained fingerprint, and test the signed upgrade on a real device before confirming. A published asset in this public repository is publicly downloadable. A URL or a manually entered fingerprint alone is not proof of safety.

The new native app checks the fixed-origin update policy, then—only when the user chooses to download—limits redirects to GitHub's release-asset hosts, limits file size, verifies the byte hash, package/version and installed signing certificate, and offers Android's installer. Android must separately allow installations from this app and the user must confirm; no silent install occurs. Android verifies installation itself. A mandatory policy blocks this updated app's workspace when the installed code is below the required code; it is **not** a server-side access control and older binaries do not enforce it. The last valid mandatory policy is retained offline or on a malformed/failed fetch until a valid replacement or explicit unpublish is received. Verify recovery from a broken release before making an update mandatory. Rollback to an older current release does not downgrade already-newer installations.

To stop future sends, disable the scheduler and server push flag; in-flight/already accepted messages cannot be recalled. Roll back code only to a backend that preserves the installed app's required APIs. Destructive database cleanup or restoring a backup needs its own reviewed plan.
