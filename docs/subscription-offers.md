# Subscription offers: operation and rollout

The code in this repository does **not** itself enable offers in an existing deployment. Migration `0017_subscription_offers.sql` and its matching application must be released together. No prices, codes or announcements are seeded by this migration.

## Owner experience

- The monthly, six-month and yearly prices remain the current all-features base prices. A term must have a configured positive price to be available. Term savings compare that price with the current monthly price multiplied by 1, 6 or 12; if a longer term is more expensive, the UI says so instead of inventing a saving. If the monthly price is unavailable, that comparison is unavailable.
- The owner chooses a term and may apply **one** code. The server calculates the promo savings from the term's base price and shows the balance and combined comparison before the owner confirms. Percentage discounts are rounded **down** to whole paise; fixed discounts are capped at the base price. A discount that rounds to zero cannot be applied. Prices and eligibility are checked again transactionally when the request starts; a stale quote must be refreshed and reviewed.
- If the balance is positive, the owner receives the exact snapshotted UPI recipient and amount, sends a one-time transfer, and submits a reference. Printly must independently verify and approve the transfer; submitting a reference never grants access. An initiated or submitted request holds its original amount and cannot be replaced with a new offer. Cancel it only if no money was sent.
- A valid 100% percentage discount **or a fixed discount that covers the full term** produces a zero balance. When the owner confirms it, access is granted immediately, without UPI or manual review. It adds one, six or twelve calendar months in Asia/Kolkata after any remaining time; permanent access needs no purchase. The request and its automatically granted period appear in shop and admin history. Positive-balance requests cannot enter this path.
- New requests snapshot the base term price, the monthly comparison price, promo code, discount, balance and (when required) UPI recipient. Admin edits, expiry or pausing a code do not rewrite existing requests or granted periods. Older requests have no savings snapshot, so the UI does not calculate their past savings from today's prices.

## Admin setup

Open **Admin → Subscription → Offers & announcements**.

1. Create a code using 3–32 letters, numbers, hyphens or underscores. Codes are case-insensitive and cannot be renamed after saving; create a new code instead. Choose a whole percentage from 1–100, or an exact fixed rupee amount, and select the eligible terms.
2. Optionally set start and end dates, entered as **India time (IST)**. A code is valid from its start (inclusive) until its end (exclusive). Blank dates have no bound. Set an optional total usage limit and optional per-shop limit. The form defaults to one use per shop; clearing that field means **unlimited**, not one. Use caps appropriate to the value of the offer.
3. An initiated or submitted paid request **reserves** a use. Cancelling an unpaid request or rejecting a report releases it; an approved request, including an automatic free activation, consumes it permanently. Reservations do not silently expire because the shop may already have paid. A total cap includes both reserved and approved uses, and is enforced atomically across simultaneous shops. Lowering a cap or pausing a code does not alter prior requests.
4. A 100% code, or a fixed discount at least as large as an eligible term price, permits free activation. With no per-shop limit a shop can redeem it repeatedly while it remains valid; the admin UI warns before saving or enabling such a code. A later change to term prices can also make a fixed discount cover an entire term, so review active codes when changing prices. Avoid unlimited free codes unless repeat extensions are intentional.
5. Create an announcement with a title and message and optionally enter any saved code, including an older one. Linked discount and term information is generated from the actual code; write neutral message text that remains accurate if a discount is edited. During its own window an enabled announcement is eligible to appear to signed-in shops; select **Show on public pricing page** to publish it there too. Each surface displays up to its 100 most recent available announcements. A linked announcement is automatically hidden while its code is paused, outside its window or fully reserved. Per-shop eligibility and limits are checked only when a shop applies the code; public visitors see a general eligibility/limits notice. An unlinked announcement is independent and will not automatically hide when a code mentioned in free text expires.
6. Edit or pause a saved code or announcement in the list. Conflicting edits from another admin are rejected; reload and review rather than overwriting them. The console lists codes and announcements newest first in separate 100-item pages; use **Older** and **Newer** to manage earlier entries. New items added while you page can shift the lists, so reload when other admins are creating offers. Approved and reserved counts are shown separately. Do not delete financial history to free a usage slot.

## Recovery and security

- A subscription request key is generated with a cryptographically random UUID and kept in essential browser local storage until the outcome is confirmed. Retrying in the **same browser** uses that key, and the database returns the existing result rather than granting the term again—even if a different term was selected while the first response was lost. Refreshing the subscription page also recovers a matching recent request. If storage is blocked, starting a request fails closed.
- Each quote also captures the current access expiry. If another tab or device activates or is approved before a second request starts, the older quote is rejected even if it used a different key; refresh the status and review a new quote. This protects simultaneous stale confirmations, not a cross-device exactly-once guarantee: a newly reviewed quote and new key can intentionally add another term, and clearing storage loses same-key recovery. Check history and access before starting again. Per-shop use limits are important, especially for free offers. If a UPI transfer may already have been sent, do not pay again or cancel it as unpaid; submit the reference or contact an administrator.
- Offer tables and mutating/quote RPCs are not accessible to `anon` or `authenticated` database roles. Server routes validate the signed-in actor and shop membership, and database RPCs additionally verify the actual owner or administrator. Promo attempts are limited per actor and shop using a separately keyed hash and the existing 30-per-15-minute checkout limiter configuration. This limits guessing but does not make weak codes secret or prevent distributed abuse. Purchase activation uses row locks and requires PostgreSQL's normal **read committed** transaction isolation; it fails closed at other isolation levels because their stale snapshots could undermine the lock-then-count protocol.
- Public pages get only the safe announcement and code fields through a server-side service-role RPC; service-role credentials must never reach a browser. Public pages show an unavailable notice on a read failure, not a fictional offer. Do not put sensitive information in an announcement or public code.

## Verification and coordinated production rollout

Production migration or deployment requires explicit operator authorization. Before any rollout, use a staging copy with representative **existing** pending and approved purchases, verify a restorable backup, inventory real data, and rehearse the migration and rollback/recovery. Confirm that the existing `0011` purchase constraints match the migration's expected names and that no anomalous legacy rows violate its stricter approved-period checks. The migration intentionally does not rewrite purchase amounts, recipients, statuses, entitlements or plan prices; compare pre/post snapshots and investigate any discrepancy rather than continuing.

Use a planned maintenance window, block old deployment/direct bypass paths and allow in-flight work to finish. Apply `0017` and deploy the matching application as a coordinated cutover, then validate current prices, shop/public visibility, owner/admin authorization, reservations, a positive-balance UPI report with independent verification, a 100% free activation, idempotent retries and expiry extension with **isolated non-financial test data**. Remove or clearly disable the test code and announcement afterward. Do not approve a real payment without independently confirming it. Older open browser tabs should refresh; an old start payload is rejected by the new API rather than silently skipping the review.

Do not roll back only the application or database: zero-amount purchases and promo references require the new schema and UI. Keep maintenance enabled and use a rehearsed, coordinated recovery that preserves existing purchases and entitlements; fix forward where possible. The migration does not grant blanket free access and does not create or publish an offer by itself.

## Tests

Run `pnpm test`, `pnpm typecheck` and `pnpm build`. The PGlite tests execute the actual migration and verify preservation, permissions, discounts, limits, snapshots, approval, free activation and retry behavior.

For real multi-backend locking tests, install local PostgreSQL binaries and run `pnpm test:subscription-concurrency` (or set `PRINTLY_PG_BIN` to the directory containing `initdb`, `postgres`, and `psql`; set any necessary library path). The optional script creates and destroys its **own temporary cluster**, binds only a private Unix socket, and never connects to an existing database. It checks migration preservation of representative existing paid requests, entitlements and plan settings; simultaneous capped activations; duplicate retries; different-key confirmations of the same stale free quote; a concurrent plan edit; a concurrent promo pause; and the non-default-isolation fail-closed guard. It needs `stdbuf` and cannot run `initdb` as root.
