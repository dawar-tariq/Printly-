# Native order notifications: candidate rollout

This document describes the **candidate**, not a deployed feature. The supplied `google-services.json` is public Android client configuration for Firebase project `printly-5c247` and package `io.github.dawartariq.printly.owner`. It is not a service-account key. It is included only in the release variant; the demo and isolated QA variants do not register with the production Firebase app. Restrict the Google API key to the appropriate Android app/signing certificate and necessary APIs in Google Cloud where compatible with Firebase's requirements. Firebase Cloud Messaging generally requires Google Play services on the phone.

## How it is intended to work

- In the native app, **More → Order notifications** asks the signed-in shop user to opt in. Android 13+ additionally requests the system notification permission. No notification registration is started automatically before opt-in.
- FCM's installation-ID callback is synced through a verified native bearer session. The server rechecks the specified shop membership and stores a private device association. Registration is rate limited and limited to ten devices per account. FIDs and tokens must not be logged or sent to analytics.
- Migration `0026` independently queues a generic alert when an order enters the queue or a customer reports a UPI payment. A shop confirmation of that same reported payment does not produce a second new-order alert. A reported payment is **not** verified or confirmed payment. The migration does not depend on the deferred browser push migration `0023`.
- A separately configured, authenticated server worker leases queued deliveries and sends **data-only** FCM messages with random event/binding IDs and a generic kind. No order ID, tracking link, customer details, payment amount or files are in the push. Tapping an alert opens the app, which fetches the authoritative order list using the user's session. A random binding changes on each opt-in; the app rejects old/in-flight messages after sign-out or a switch of account. Local display is disabled immediately, while remote removal is attempted before session revocation. If offline, the app retries FCM unregistration when connected; a running worker also sweeps server registrations that have not synced for 180 days. A failed remote removal is reported to the user.
- The outbox is best-effort and at-least-once. Retries can duplicate a send after a crash; the app uses the event ID as the notification tag. Expired work is not sent after 24 hours, and events are deleted after seven days by the worker. FCM acceptance is not proof of delivery. Force-stopping the app, Android battery restrictions, no internet, disabled notifications, missing Google Play services, service outages or maintenance can delay/prevent alerts. Use the order board as the source of truth.

## Required private server setup — **not configured yet**

A user-controlled operator must first approve and provision a **separate test environment**, then approve production changes. Never paste a private key, bearer secret, OAuth token, refresh token or service-account JSON into chat, the repository or a workflow log.

1. Enable the Firebase Cloud Messaging API for the intended Google project. Create a dedicated service identity with only the permissions needed to send FCM HTTP v1 messages. The server supports a same-project service-account JSON, not the downloaded Android client JSON. Prefer a managed, keyless identity if the hosting environment supports it; this candidate currently needs a service-account JSON if running on Vercel, so treat that key as a sensitive long-lived credential and plan rotation/revocation.
2. In the hosting provider's **private, sensitive server environment settings**, set `PRINTLY_FCM_SERVICE_ACCOUNT_JSON` to that service account's JSON, `PRINTLY_NATIVE_PUSH_CRON_SECRET` to an independently generated random URL-safe secret of 32–128 characters, and only after the scheduler is ready set `PRINTLY_NATIVE_PUSH_ENABLED=1`. These values must never use `NEXT_PUBLIC_` names. The worker rejects a different project, malformed key, missing switch or weak scheduler secret. The client config does not substitute for these credentials.
3. Configure a trusted scheduler to call `GET` or `POST /api/cron/native-order-push` over HTTPS with `Authorization: Bearer <the private scheduler secret>`. Do not put the secret in a URL. Use a secret manager/vault, restrict access, monitor non-200 responses and avoid overlapping invocations. One-minute scheduling is a practical target, **not** a delivery guarantee. This repository does not install a scheduler. Vercel Hobby Cron is limited to daily and is not suitable for near-real-time alerts; a suitable external scheduler, Supabase Cron/pg_net with protected vault secrets, or an eligible paid Vercel plan is required. Check current quotas and costs first. The worker is subject to maintenance middleware, so during maintenance it cannot dispatch and older messages can expire.
4. Apply migrations `0025` and `0026` only with explicit database-change approval and a verified rollback/backup plan. `0025` requires the existing `supabase_realtime` publication and now fails rather than silently skipping it. `0026` creates private tables, triggers and service-only functions; it does not send network requests. Do not accidentally include unrelated deferred migrations `0022`–`0024`.
5. Deploy the reviewed website/server build and verify it against a disposable backend before any production promotion. Enable the private worker only after credentials and scheduler are safely configured. Test with synthetic orders, a real supported phone, explicit consent, app backgrounded/closed, sign-out, a second account/shop, offline recovery and permission denial. Verify the two shop identities cannot receive each other's notifications. A real FCM send and phone test have **not** happened yet. The current isolated QA build has no Firebase configuration, so a separate test Firebase app/project and a QA-enabled variant must be provisioned before a safe full end-to-end test; do not point a debug/QA package at production as a shortcut.
6. After successful tests and explicit approval, increment the native version code, make a new signed review using the independently verified release key, test an upgrade over the installed signed app, and separately authorize publication. The earlier `native-v2.0.1` draft does not contain these changes. A published GitHub Release asset is publicly accessible even if the dashboard link requires login.

## Monitoring and rollback

The worker reports counts of leased, FCM-accepted, retried, unregistered, discarded and unconfirmed deliveries, never device identifiers or payloads. Alert on failures, unconfirmed leases, sustained retries and the age/volume of pending work using a restricted operational channel. Configure scheduler timeouts and ensure only the intended project/host is targeted. Queue leases prevent concurrent workers from claiming the same row, but cannot guarantee exactly-once delivery or recall a message already accepted by FCM.

For an emergency stop, disable the scheduler and set `PRINTLY_NATIVE_PUSH_ENABLED=0`, then redeploy/restart as required by the host. The app still rejects old messages locally after opt-out/sign-out, and the authenticated deletion endpoint remains available while the feature flag is off (except during site maintenance). To remove all server-side registrations/outbox or drop triggers/functions/tables, use a separately reviewed, approved database rollback with a backup; this is a destructive change and does not recall already accepted messages. Keep Firebase signing credentials private and revoke/rotate any exposed service-account key. Foreground order refresh and customer tracking can continue independently of the push worker.
