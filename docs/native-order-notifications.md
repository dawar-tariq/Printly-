# Native order notifications: candidate rollout

This document describes the **candidate**, not a production-enabled feature. A disabled candidate has been deployed only to the isolated test environment described below. The release variant uses public Android client configuration for Firebase project `printly-5c247` and package `io.github.dawartariq.printly.owner`. The isolated, debug-signed QA variant uses a different public client configuration: project `printly-notifications-qa`, package `io.github.dawartariq.printly.owner.native.qa`. The demo has no Firebase implementation. QA and release share the opt-in push code but never share Firebase identities; QA is additionally pinned to the dedicated test website and staging Auth host. These Android client files are not service-account keys and cannot authorize a server send. Restrict each Google API key to the appropriate Android app/signing certificate and necessary APIs in Google Cloud where compatible with Firebase's requirements. Firebase Cloud Messaging generally requires Google Play services on the phone.

## How it is intended to work

- On first open, the push-capable QA and release variants ask for Android's system notification permission on Android 13+; the synthetic demo does not. The prompt is not automatically repeated on later opens, including after denial. Earlier Android versions do not have this runtime prompt. Permission alone does not enable FCM or register a device. A signed-in shop user must still explicitly opt in under **More → Order notifications**, where they can request permission again when appropriate or open the phone settings. No notification registration is started automatically before opt-in.
- FCM's installation-ID callback is synced through the same verified native bearer session that opted in. Each sign-in has a new random local session identity, retained across token refresh; older encrypted sessions are upgraded when restored. The server rechecks the specified shop membership and stores a private device association. Registration is rate limited and limited to ten devices per account; deletion has a separate rate limit. FIDs and tokens must not be logged or sent to analytics.
- Migration `0026` independently queues a generic alert when an order enters the queue or a customer reports a UPI payment. A shop confirmation of that same reported payment does not produce a second new-order alert. A reported payment is **not** verified or confirmed payment. The migration does not depend on the deferred browser push migration `0023`.
- A separately configured, authenticated server worker leases queued deliveries and sends **data-only** FCM messages with random event/binding IDs and a generic kind. No order ID, tracking link, customer details, payment amount or files are in the push. Tapping an alert opens the app, which fetches the authoritative order list using the user's session. A random binding changes on each opt-in; display and background registration require the same local session identity, so old/in-flight messages are rejected after sign-out or an account switch.
- Opt-out disables display immediately and attempts server removal with the **same** session; leaving the settings screen does not cancel that attempt. Sign-out also removes local access before waiting for the network, then attempts server removal and Auth logout using the captured **old** bearer, not a newer account's session. A bounded list of earlier unconfirmed removals is retried at sign-out only while the app process remains alive; it is not durable storage or a guarantee. Removal can fail, especially offline or if that bearer has expired; a failure shown on screen is not a promise of remote revocation. A confirmed server removal also records a user-scoped binding revocation for seven days to reject late registrations; it is not an indefinite revocation mechanism. If offline, the app schedules FCM unregistration retries; late Firebase register/unregister callbacks reconcile against current consent. A running worker sweeps registrations that have not synced for 180 days. None of these mechanisms can guarantee cleanup if the app is force-stopped, uninstalled, or never reconnects.
- The outbox is best-effort and at-least-once. Retries can duplicate a send after a crash; the app uses the event ID as the notification tag to collapse duplicates **while the notification is still present**, not after it has been dismissed. A late FCM unregistered response cannot remove a more recently refreshed device association; its delivery is retried instead. Expired work is not sent after 24 hours, and events are deleted after seven days by the worker. FCM acceptance is not proof of delivery. Force-stopping the app, Android battery restrictions, no internet, disabled notifications, missing Google Play services, service outages or maintenance can delay/prevent alerts. Use the order board as the source of truth.

## Required private server setup — **not configured yet**

A user-controlled operator must separately approve any **test worker credentials, scheduler or real FCM send**, and separately approve production changes. Never paste a private key, bearer secret, OAuth token, refresh token or service-account JSON into chat, the repository or a workflow log. The client configuration alone does not enable the worker, deploy the server, apply migrations, or demonstrate FCM delivery.

1. Enable the Firebase Cloud Messaging API for the intended Google project. Create a dedicated service identity with only the permissions needed to send FCM HTTP v1 messages. Use a **QA-project** service account for isolated testing; never put the production account or key in the QA project. The server supports a same-project service-account JSON, not the downloaded Android client JSON. Prefer a managed, keyless identity if the hosting environment supports it; this candidate currently needs a service-account JSON if running on Vercel, so treat that key as a sensitive long-lived credential and plan rotation/revocation.
2. In the intended hosting project's **private, sensitive server environment settings**, set `PRINTLY_FCM_SERVICE_ACCOUNT_JSON` to that environment's service account JSON, `PRINTLY_NATIVE_PUSH_CRON_SECRET` to an independently generated random URL-safe secret of 32–128 characters, and only after the scheduler is ready set `PRINTLY_NATIVE_PUSH_ENABLED=1`. These values must never use `NEXT_PUBLIC_` names. The worker selects the QA Firebase project and package only when the complete dedicated test Vercel/Supabase isolation guard passes; a partially configured test-looking environment is rejected, not treated as production. It selects the production identity otherwise and rejects a wrong-project account, malformed key, missing switch or weak scheduler secret. The guard detects some wrong Supabase keys but cannot establish the project behind a newer opaque key; the operator must independently verify both backend keys and the server environment. The client config does not substitute for these credentials.
3. Configure a trusted scheduler to call `GET` or `POST /api/cron/native-order-push` over HTTPS with `Authorization: Bearer <the private scheduler secret>`. Do not put the secret in a URL. Use a secret manager/vault, restrict access, monitor non-200 responses and avoid overlapping invocations. One-minute scheduling is a practical target, **not** a delivery guarantee. This repository does not install a scheduler. Vercel Hobby Cron is limited to daily and is not suitable for near-real-time alerts; a suitable external scheduler, Supabase Cron/pg_net with protected vault secrets, or an eligible paid Vercel plan is required. Check current quotas and costs first. The worker is subject to maintenance middleware, so during maintenance it cannot dispatch and older messages can expire.
4. Apply migrations `0025` and `0026` only with explicit database-change approval and a verified rollback/backup plan. `0025` requires the existing `supabase_realtime` publication and now fails rather than silently skipping it. `0026` creates private tables, triggers and service-only functions; it does not send network requests. Do not automatically include unrelated migrations `0022`–`0024`; staging already had `0022`, while `0023` and `0024` remain deferred.
5. The reviewed candidate and required migrations have been prepared on the isolated test site and staging backend only, as recorded above. Before further changes, recheck the server's actual backend and project settings, not just the website hostname. With separate approval, enable the private worker only after QA credentials and a test-only scheduler are safely configured. Test with synthetic orders, a real supported phone, explicit consent, app backgrounded/closed, sign-out, a second account/shop, offline recovery and permission denial. Verify the two shop identities cannot receive each other's notifications. A real FCM send and phone test of the updated QA APK have **not** happened yet. The QA client configuration is present in code, but no corresponding server credential or scheduler has been provisioned; do not point a QA package at production as a shortcut.
6. After successful tests and explicit approval, increment the native version code, make a new signed review using the independently verified release key, test an upgrade over the installed signed app, and separately authorize publication. The earlier `native-v2.0.1` draft does not contain these changes. A published GitHub Release asset is publicly accessible even if the dashboard link requires login.

## Monitoring and rollback

The worker reports counts of leased, FCM-accepted, retried, unregistered, discarded and unconfirmed deliveries, never device identifiers or payloads. Alert on failures, unconfirmed leases, sustained retries and the age/volume of pending work using a restricted operational channel. Configure scheduler timeouts and ensure only the intended project/host is targeted. Queue leases prevent concurrent workers from claiming the same row, but cannot guarantee exactly-once delivery or recall a message already accepted by FCM.

For an emergency stop, disable the scheduler and set `PRINTLY_NATIVE_PUSH_ENABLED=0`, then redeploy/restart as required by the host. The app still rejects old messages locally after opt-out/sign-out, and the authenticated deletion endpoint remains available while the feature flag is off (except during site maintenance). To remove all server-side registrations/outbox or drop triggers/functions/tables, use a separately reviewed, approved database rollback with a backup; this is a destructive change and does not recall already accepted messages. Keep Firebase signing credentials private and revoke/rotate any exposed service-account key. Foreground order refresh and customer tracking can continue independently of the push worker.
