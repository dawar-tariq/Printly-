# Security review and release checklist

This is a practical code and configuration review, not an independent penetration test, legal review or guarantee of security. Tests exercise selected routes and database privileges; they do not establish that every authorization path, provider setting, browser or deployment is safe. Review infrastructure, logs, backups, dependencies and third-party settings continuously.

## Changes in this release

- Migration `0012` removes client access to individual review rows (which included bearer order IDs), direct dispute writes and the tracking RPC. The application uses service-role server routes for those operations. It also removes several unnecessary client write grants. Existing database policies and application authorization still matter.
- Migrations `0013`/`0014` and the server limiter provide shared, atomic per-IP windows for selected routes including shop applications, login UI preflight, order starts, uploads, draft edits/quotes, new checkouts, tracking, Dropbox imports and feedback. Original and edited upload links also share a 30-per-draft allowance so a draft cannot create unlimited signed URLs merely by omitting finalization. Dropbox imports have a separate per-draft allowance. Only keyed IP/draft hashes are stored. A limit is not a replacement for authentication, cleanup, bot protection, provider limits or infrastructure-level DDoS controls. See trusted-proxy requirements and exact limits in the README.
- Migration `0015` enforces one open/investigating dispute per order and maintains rating totals from all review rows in the database rather than a capped or stale API result. It snapshots existing displayed totals before recalculating them; this is not an independent backup. The dashboard retains its last full order snapshot and warns if refresh fails, rather than silently showing empty lanes. Tracking and board polling pause in hidden tabs.
- Sign-out uses local rather than global scope, checks the provider's unsuppressed response for the current session, and then attempts browser cleanup. It warns instead of retrying blindly when revocation is uncertain: the SDK can remove the local token before a failed request and suppress some 401/403/404 errors. Even after confirmed revocation, previously issued access tokens can remain valid until expiry. New passwords in the application require at least 12 characters and no more than 72 UTF-8 bytes. These app rules and checks cannot enforce the same policy against direct Supabase Auth calls.
- JSON request bodies and name-proof multipart uploads are bounded while reading, including requests without a reliable Content-Length. Over-limit/invalid input is rejected; these application limits do not replace hosting limits or protect direct provider endpoints.
- Middleware rejects cross-origin browser mutations to application APIs, including sibling origins; requests without browser origin metadata still require their normal authentication or order-session authorization. Production headers add framing, referrer, MIME-sniffing and content-security restrictions. CSP still allows inline scripts/styles; it does not eliminate XSS.
- Shop QR generation requires a validated canonical site origin instead of trusting a request Host header. Sensitive routes are marked noindex and/or no-store where configured. Robots rules and noindex are not access controls and cannot remove previously indexed or leaked links.
- Vulnerable production dependency versions identified during the review were upgraded/overridden; an audit is a point-in-time check against known advisories, not proof that dependencies are safe.

## Important remaining risks and operator actions

1. **Verified onboarding and abuse controls.** Shop signup currently creates email-confirmed accounts through the admin API without verifying ownership of the supplied email. Configure production SMTP and a tested confirmation/recovery flow, then change onboarding so confirmation is actually required. Direct provider signup can be disabled without disabling privileged admin creation, but this does not verify email ownership. CAPTCHA is not implemented or enabled. The login limit is only a UI preflight and is bypassable through direct Supabase Auth requests; the provider's token endpoint has its own per-IP limit (observed as 150 requests per five minutes, including refreshes, with bursts up to 30), not a per-account lockout. Configure and monitor suitable provider-level protection; implement compatible CAPTCHA on the app first. Apply a provider-side password policy and current-password requirement too. Selected app limits do not stop distributed attacks, and real client IP trust must be verified.
2. **Demo credentials.** Historical seed credentials are public. They are appropriate only for isolated development. If an open demo is intentionally retained, regard its shop account and its files/orders as exposed to anyone with those credentials; do not put sensitive information there. The operator must decide when to rotate/disable it and should not rely on it for real orders.
3. **Tracking links and uploads.** Anyone with a tracking link can view the associated tracking information and can submit certain feedback. Keep links secret; they may appear in browser history, copied messages and server/provider logs. Order files use private storage and short-lived access links, but recipients can download or copy them. Cropping a PDF is not redaction. Signed links cannot be revoked by maintenance mode before expiry.
4. **Retention and recovery.** No scheduled order-file purge or automated orphan-cleanup job is implemented. A lost signup or profile/proof-update response may deliberately leave an unconfirmed account or name-proof object intact so a committed application is not damaged; investigate references before cleanup. Define, implement and verify retention, deletion and incident procedures, including shop-held copies and backups. A same-database table copy is not a complete independently restorable backup; verify restores of database, Auth and Storage separately.
5. **Payment and account operations.** UPI references are reports, not proof of payment; staff or administrators must independently verify recipient, amount and transfer. Refunds are not automatic. Use strong unique passwords, limit administrator/staff access, review audit logs and revoke access promptly when needed. Although provider TOTP settings may be enabled, this application does not yet implement MFA enrollment/challenge or enforce AAL2 consistently across its APIs and database policies. Do not treat MFA as protecting the portal until that entire flow and recovery are implemented and tested.
6. **Deployment validation.** The new limiter must see an edge-controlled single client IP, and the matching migrations and server-only service key must be present. A misconfigured proxy, RPC or key returns 503 rather than silently disabling limits. An unsafe proxy configuration can allow IP spoofing. Shared networks may hit limits together. Exercise the production CSP, CSRF checks, Dropbox Chooser, uploads, printing, login and subscription workflows on actual devices before relying on them.
7. **Business and legal content.** The public pages deliberately do not invent a business name, address or support email. Supply a real contact channel and obtain legal review tailored to the operator, jurisdiction, data practices and contracts before treating the policies as complete.

## Verification to repeat

Run `pnpm test`, `pnpm typecheck`, `pnpm build` and `pnpm audit --prod` after changes. Verify grants and row-level policies on the actual target database, and inspect production HTTP headers and proxy behavior. Use isolated test accounts, files and non-financial transactions for end-to-end smoke tests; do not approve or send real payments as a test. Confirm cleanup without deleting real customer data. Document anything not tested, any failures and the precise deployed versions.
