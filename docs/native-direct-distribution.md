# Native Android direct-download release plan

**Status: preparation only.** The native gateway and direct-download page have not been deployed to the live site, no native release APK has been signed or published, and no database or Storage backup has been independently verified. The operator reports recent backups and a successful restore test. The debug APK is synthetic and must never be offered as a production download. The public repository and Actions artifacts must not contain signing keys, passwords, customer data or an unencrypted review APK.

The requested distribution is a signed Android APK available from the signed-in shop dashboard, beside **Settings & QR**. The page remains unavailable until complete release metadata is configured; metadata validation does **not** itself prove an APK's identity or signature. The installed native app's **More → Check for app updates** opens this fixed website page in the browser. The browser may require a separate shop sign-in. No APK is installed silently and no session token is placed in the link.

## Gates before a live release

1. **Recoverability:** arrange a recent, access-controlled, independently verified database backup **and** separate Storage object backup; a signing-key backup is not either. Check what the backups include, consistency during concurrent writes, retention, a safe isolated restore test and an operator-owned recovery procedure. Never put real shop data or backup credentials in Git, Actions artifacts or chat. The available connector cannot inspect the provider's backup inventory or perform a restore.
2. **Isolated end-to-end test:** the successful offline Android emulator and disposable local gateway tests are complementary, not an end-to-end physical-device test. Provide an isolated HTTPS website for the existing test Supabase project with synthetic users/data, then build the distinct `qa` package as described in the Android README. It uses a debug key and pins Auth to that staging project, but a different website hostname alone does not prove its server-side backend is isolated. Verify the effective site and Supabase projects before login or writes. Existing Vercel Preview defaults point at production and are not suitable as staging. When last checked, the branch's Vercel alias also pointed at the promoted **production** deployment; do not use or repoint it for staging. Use a separately isolated site accessible from the test phone, without embedding a preview-bypass secret in the APK. Staging currently has a different migration history from production. Test login/session refresh and expiry, membership and cross-shop denial, offline/reconnect, orders and payment review, files, QR, inventory/rate conflicts, and expired subscriptions and recovery. Separately verify upgrade compatibility with the actual release identity on a physical phone.
3. **Production security and operational review:** review the exact clean source and lockfiles, auth and RLS, accessibility, error recovery, support and legal copy, expected load, monitoring and rollback. The native app does not provide background notifications, in-app printing, native signup/password recovery, bulk rate changes, or a complete accounting ledger; see `apps/printly-owner-native-android/README.md` for limits. The production `orders` table was not in the Realtime publication when checked. The board falls back to foreground polling; enabling Realtime requires a separate reviewed publication/RLS and capacity plan. No new production migration is needed merely to deploy the current native gateway.
4. **Signing and upgrade identity:** independently compare the public signing certificate in the protected backup with the signer and version of any already installed owner APK. Verify compatibility before replacing it; never ask owners to uninstall a real app simply to bypass a signature mismatch. Review the exact Android code, Gradle inputs and signing workflow because build code runs with access to the release key. Keep the long-lived key and its backup private. Version code 4 and name 2.0.1 are proposed, not proof that a compatible update can be installed over every existing package.
5. **Release and rollback:** agree on a pilot/rollout and monitor errors, login, data access and download integrity. The current older production website does not have the native gateway: rolling back to it after people install the native APK would break that app. Disabling the download stops new downloads, but does not remove installed APKs or undo business writes. Prepare a compatible rollback/hotfix and data recovery plan before publishing.

The test domain is publicly reachable: noindex is not access control. Never put real shop accounts, customer data, files, real UPI IDs, or live integrations there. The operator reports that staging data, files and UPI details are synthetic and enabled test accounts have strong private passwords; this was not independently verified. When inspected, staging had one seed shop, four seed orders, one additional order and one Storage object. The staging schema has migration `0022`, which is absent from production.

Test the flows in gate 2 above, including cross-shop denial with a separately provisioned synthetic shop. Record failures and retest. Do not expose the production download or request real signing based solely on this rehearsal.

## Protected native signing review

`.github/workflows/android-native-release-review.yml` is review-only and does not publish, alter the website or change the database. It reuses the `printly-owner-signing` GitHub environment and its existing protection checks; the environment must require a reviewer, forbid administrator bypass and allow only the exact current branch. The operator must independently confirm those controls and the public fingerprint. The workflow verifies encryption on harmless data before the signing step, builds the **native** release, verifies the package, manifest, version and single signer, and uploads only an encrypted review APK plus public evidence. The ordinary Android workflow exercises the same signer and request checks with a disposable CI key; that key is never suitable for release.

After the gates above are met and the operator has reviewed the precise commit, copy `signed-review-request.example.json` to `signed-review-request.json` in the native app directory, provide a unique request ID and independently verified public fingerprint, and deliberately commit that request on the current branch. The protected environment reviewer must examine and approve the exact run; the example file does not trigger signing. See `docs/android-signing-review.md` for environment secret names and secure handling; do not paste secrets into chat. The workflow and all source/dependencies must be reviewed before approval.

Download and decrypt the review artifact on a trusted operator device. Independently use Android `apksigner verify --verbose --print-certs`, inspect package/version/permissions with Android SDK tools, and compute the APK SHA-256. Compare all of these with the trusted certificate and workflow evidence; install and test it on a physical device. An encrypted artifact or passing CI is not proof of successful decryption or a working installed app.

## Publication once verified

Publish **only the verified signed native APK** at a stable HTTPS URL on this site's `/downloads/<file>.apk` or as an asset of this repository's GitHub Releases. A GitHub release asset is publicly downloadable by anyone with the URL even though the dashboard page requires a shop session. Do not commit the APK or any credentials to the repository. Before exposing the link, independently download the hosted bytes and recheck their SHA-256, Android signer, package and version against the tested APK.

Configure these values for the intended server environment, then deploy and check the signed-in dashboard and direct download:

- `PRINTLY_ANDROID_VERSION_CODE` — positive integer matching the actual APK.
- `PRINTLY_ANDROID_VERSION_NAME` — bounded version label matching the APK.
- `PRINTLY_ANDROID_APK_URL` — the stable approved HTTPS `.apk` URL.
- `PRINTLY_ANDROID_APK_SHA256` — 64-character SHA-256 of the APK bytes, not the certificate.
- `PRINTLY_ANDROID_RELEASE_NOTES` — optional plain-text release notes, up to 400 characters.
- `NEXT_PUBLIC_SITE_URL` — canonical HTTPS origin, with no path or query.

Invalid or missing values hide the link. Android may warn about installations outside Google Play and asks the user to approve installation; never tell users to disable Play Protect. For a later Play Store launch, plan Google Play App Signing and the direct-install signing identity **before** enrollment so that updates can be compatible; the Play app-signing key and an upload key can differ. A switch to Play is not automatic and requires its own testing and publication process.
