# Native Android direct-download release plan

**Status: gateway deployed; APK release pending device test.** The tested web candidate is live on `https://printly0.vercel.app`; the former `printly-steel-three.vercel.app` address redirects there. A protected run produced an unpublished signed native release draft, but no native APK has yet been published. The operator reports recent, separately restore-tested production database and uploaded-file backups, but those backups were not independently inspected. The debug APK is test-only and must never be offered as a production download. Never put signing keys, passwords or customer data in the public repository, release assets or Actions artifacts.

The requested distribution is a signed Android APK available from the signed-in shop dashboard, beside **Settings & QR**. The page remains unavailable until complete release metadata is configured; metadata validation does **not** itself prove an APK's identity or signature. The 2.1.0 candidate adds **More → Check for app updates** inside the native app, with user-initiated download, verification and Android installer confirmation. A debug-signed isolated QA binary has been built and installed, but the update flow has not been tested end to end on a device and no 2.1.0 release APK has been signed. Older reviewed builds retain the previous website-link behavior. See `docs/native-notification-management.md` for managed-feed, rollback and mandatory-update limits.

## Gates before a live release

1. **Recoverability:** the operator reports recent production database **and** uploaded-file backups, both restored in a separate environment. This is not independent verification; a signing-key backup is not either. Check coverage, consistency during concurrent writes, retention and an operator-owned recovery procedure. Never put real shop data or backup credentials in Git, Actions artifacts or chat. The available connector cannot inspect the provider's backup inventory or perform a restore.
2. **Isolated end-to-end test:** the successful offline Android emulator and disposable local gateway tests are complementary, not an end-to-end physical-device test. A separate HTTPS test site and distinct debug-signed `qa` package are available; the operator reports a successful partial phone rehearsal and no real money transferred. See `docs/native-owner-validation.md` for the reported scope and its limits. The QA package pins Auth to staging, but a different website hostname alone does not prove its server-side backend is isolated; verify the effective site and Supabase projects before login or writes. Existing Vercel Preview defaults point at production and are not suitable as staging. When last checked, the branch's Vercel alias also pointed at the promoted **production** deployment; do not use or repoint it for staging. Use the separately isolated site accessible from the test phone, without embedding a preview-bypass secret in the APK. Staging currently has a different migration history from production. Complete and document coverage for login/session refresh and expiry, membership and cross-shop denial, offline/reconnect, orders and payment review, files, QR, inventory/rate conflicts, and expired subscriptions and recovery. Separately verify upgrade compatibility with the actual release identity on a physical phone.
3. **Production security and operational review:** review the exact clean source and lockfiles, auth and RLS, accessibility, error recovery, support and legal copy, expected load, monitoring and rollback. The native app candidate includes opt-in background notifications, which require separate server/scheduler rollout and further device testing. It does not provide in-app printing, native signup/password recovery, bulk rate changes, or a complete accounting ledger; see `apps/printly-owner-native-android/README.md` for limits. A recent read-only production metadata check found the `orders` table in the Realtime publication with RLS enabled, unlike an earlier snapshot; this is not proof of cross-shop privacy, and the difference needs investigation. The board falls back to foreground polling; review the actual publication, RLS and capacity before a rollout. No production change was made by that check. The legacy gateway alone can run on the prior schema, but the notification/update candidate requires migration 0027 and a coordinated server rollout. Production migration history was observed through `0021`, and the native push and managed notification/release schemas were absent in the read-only inventory; reconcile the full ordered migration plan before any approved change. Migration 0027 and the matching server were deployed only to isolated QA, with delivery paused; they have not been rolled out to production.
4. **Signing and upgrade identity:** the public certificate in the protected backup matches the recorded earlier review fingerprint. The operator reports there are no existing non-test owner-app installations. If that changes, independently compare the installed app's signer and version before replacing it; never ask owners to uninstall a real app simply to bypass a signature mismatch. Review the exact Android code, Gradle inputs and signing workflow because build code runs with access to the release key. Keep the long-lived key and its backup private. The earlier reviewed code 4/name 2.0.1 and local candidate code 5/name 2.1.0 do not prove compatibility with an unknown installation.
5. **Release and rollback:** agree on a pilot/rollout and monitor errors, login, data access and download integrity. The previous production deployment does not have the native gateway: rolling back to it after people install the native APK would break that app. Disabling the download stops new downloads, but does not remove installed APKs or undo business writes. Prepare a compatible rollback/hotfix and data recovery plan before publishing.

## Protected native signing review

`.github/workflows/android-native-release-review.yml` does not publish, alter the website or change the database. It reuses the `printly-owner-signing` GitHub environment and its existing protection checks; the environment must require a reviewer, forbid administrator bypass and allow only the exact current branch. The operator must review the precise commit and public fingerprint. The workflow verifies encryption on harmless data before signing, builds the **native** release, checks its package, manifest, version, production hosts and single signer, and uploads an encrypted Actions artifact plus public evidence. It then creates an **unpublished GitHub release draft** containing the same APK for an authorized device test, checks GitHub's asset digest, downloads the hosted bytes again, and rechecks their checksum, signer, package and version. A draft is visible to repository writers and is not a public release; do not put sensitive data in the APK. The ordinary Android workflow exercises the signer and request checks with a disposable CI key; that key is never suitable for release.

After the gates above are met and the operator has reviewed the precise commit, copy `signed-review-request.example.json` to `signed-review-request.json` in the native app directory, provide a unique request ID and independently verified public fingerprint, and deliberately commit that request on the current branch. The protected environment reviewer must examine and approve the exact run; the example file does not trigger signing. See `docs/android-signing-review.md` for environment secret names and secure handling; do not paste secrets into chat. The workflow and all source/dependencies must be reviewed before approval.

After a successful protected run, a repository writer can download the APK from the unpublished GitHub release draft for a physical-device test. The draft targets production: use an authorized shop account and avoid real payments or unintended writes. Independently use Android `apksigner verify --verbose --print-certs`, inspect package/version/permissions with Android SDK tools, and compute the APK SHA-256 when possible. Compare these with the trusted certificate and workflow evidence; passing CI alone is not proof of a working installed app. The encrypted Actions artifact is also available for independent decryption with the separately stored passphrase; never send the passphrase in chat.

## Publication once verified

Publish **only the verified signed native APK** at a stable HTTPS URL on this site's `/downloads/<file>.apk` or as an asset of this repository's GitHub Releases. A GitHub release asset is publicly downloadable by anyone with the URL even though the dashboard page requires a shop session. Do not commit the APK or any credentials to the repository. Before exposing the link, independently download the hosted bytes and recheck their SHA-256, Android signer, package and version against the tested APK.

The legacy shop-download feed uses the values below. The separate, disabled-by-default managed release feed has a different rollout, validation and unpublish behavior; see `docs/native-notification-management.md`. For a separately approved legacy release, configure these values for the intended server environment, then deploy and check the signed-in dashboard and direct download:

- `PRINTLY_ANDROID_VERSION_CODE` — positive integer matching the actual APK.
- `PRINTLY_ANDROID_VERSION_NAME` — bounded version label matching the APK.
- `PRINTLY_ANDROID_APK_URL` — the stable approved HTTPS `.apk` URL.
- `PRINTLY_ANDROID_APK_SHA256` — 64-character SHA-256 of the APK bytes, not the certificate.
- `PRINTLY_ANDROID_RELEASE_NOTES` — optional plain-text release notes, up to 400 characters.
- `NEXT_PUBLIC_SITE_URL` — canonical HTTPS origin, with no path or query.

Invalid or missing values hide the link. Android may warn about installations outside Google Play and asks the user to approve installation; never tell users to disable Play Protect. For a later Play Store launch, plan Google Play App Signing and the direct-install signing identity **before** enrollment so that updates can be compatible; the Play app-signing key and an upload key can differ. A switch to Play is not automatic and requires its own testing and publication process.
