# Printly

Printly is a Next.js and Supabase application for customer print orders, shop operations, and platform administration.

## Run locally

1. Install dependencies with `pnpm install`.
2. Copy `.env.example` to `.env.local` and configure the Supabase URL, anon key, service-role key, and site URL. The service-role key is server-only; never commit it or expose it in the browser.
3. Apply all SQL migrations in `supabase/migrations` in order, including `0007`–`0009` for shop identities and privacy, `0010` for transactional checkout safeguards, `0011` for subscriptions, `0012`–`0015` for security, abuse controls and feedback integrity, `0016` for opt-in duplex-sheet rates, `0017` for subscription offers, and `0018`–`0020` for board/tracking limits, private support and UPI duplicate warnings. The application and database changes must be released together; see the rollout notes below.
4. Run `pnpm dev`. Checks: `pnpm typecheck`, `pnpm test`, and `pnpm build`.

Older migrations rely on Supabase's historical default grants for some legacy tables. A newly provisioned project may have different defaults: the isolated rehearsal needed a staging-only grant alignment to match production before the app's service role could access those tables. Review the required service-role privileges, column grants and RLS policies for each environment; do not grant broad browser access to private tables.

### Security and public-site rollout

- Review `docs/security-review.md`, the public policy wording, and the operator's legal/business details with an appropriate professional before relying on or publishing the policies. No public support email or legal entity/address is supplied by this repository; do not fill in fictitious details.
- Apply `0012`–`0015` before deploying the matching application, after a verified backup and compatibility review. `0012` removes direct client privileges for reviews, dispute writes and tracking RPC calls; their supported paths use server routes. `0013`/`0014` provide the distributed limiter; a missing RPC, service-role key or trusted IP fails limited routes closed with HTTP 503. `0015` requires at most one open/investigating dispute per order; resolve existing duplicates before applying it, without deleting their history. It snapshots prior shop-rating totals in the service-role-only `pre_0015_shop_ratings` table, then recalculates the displayed totals from stored review rows. Historical totals whose individual reviews are absent will therefore change. The snapshot is not an independent backup. Do not roll back the schema independently of code that requires it.
- Set `NEXT_PUBLIC_SITE_URL` to the real canonical site **origin** (HTTPS in production; no path, query, fragment or credentials). It is used for QR links, social metadata and the sitemap, not inferred from a request's Host header. Public subscription pricing reads only the three configured prices server-side on each request; it displays an unavailable state if they cannot be read. Never make the service-role key public.
- On Vercel, the limiter requires Vercel's edge-controlled `X-Vercel-Forwarded-For` header. A proxy placed in front of Vercel may make multiple users share the proxy IP; confirm actual edge behavior before deploying. On other production hosts, set `PRINTLY_TRUST_PROXY_IP=1` **only** if a trusted reverse proxy strips any incoming `X-Printly-Client-IP`, writes that header with exactly one verified client IP, and blocks direct access to the application. Otherwise leave it unset: the limited routes fail closed. Ordinary `X-Forwarded-For` is deliberately ignored because Next.js can synthesize it from the peer address when no proxy header was supplied. The cross-origin check also needs the real public Host and a proxy-overwritten `X-Forwarded-Proto`. Do not pass user-supplied forwarding headers through unchanged.
- The fixed-window limits share a bucket for clients behind the same IP and do not stop distributed attacks. Selected limits include 12 login-screen attempts/10 minutes; 60 upload links/15 minutes per IP and 30 original/edit links per draft lifetime; 120 expensive file validations/15 minutes; 180 draft changes/quotes per 15 minutes; 30 new checkouts/15 minutes; and, for tracking, both 6,000 reads/10 minutes per IP and 300 reads/10 minutes per IP-and-order. Support is limited to 8 new conversations/hour per IP, 180 access attempts/10 minutes per IP, 40 replies/hour per IP and 30 replies/hour per conversation. Already-started payment recovery is not charged to the new-checkout bucket. Dropbox imports retain their IP limit and also have a 20-attempt per-draft limit. These are not limits on every endpoint, and a determined distributed attacker can still incur cost. Entries contain keyed hashes rather than raw IPs or draft IDs and are cleaned opportunistically after expiry; a quiet service may retain expired hashes until later activity. Rotating the service-role key resets effective buckets and invalidates draft cookies. Local development uses a shared development bucket but still needs the migrations.
- The login-screen gate is **only a preflight for the normal UI**; it can be skipped by calling Supabase Auth directly. Supabase Auth must independently rate-limit and monitor its token endpoint. The observed project default is 150 token requests per five minutes per IP with a burst of up to 30, shared with token refreshes, not a per-account lockout. Configure and test stronger provider-level anti-bot controls. Do not enable provider CAPTCHA until compatible challenge widgets/tokens have been implemented and tested in sign-in and password verification; the app's admin-created shop signup also needs its own server-side bot verification. CAPTCHA is not configured by this repository.
- To prevent bypassing the shop application through direct Auth signup, disable public signup in Supabase Auth while retaining the privileged server-side application flow; verify the latter after any change. This does **not** verify an applicant's email. New passwords must satisfy the app's 12-character/72-UTF-8-byte rule; configure the corresponding Supabase Auth password policy independently because direct provider updates do not pass through the app. The password-change screen checks the current password, but the provider must also require it to prevent direct API bypass.
- After deployment, check same-origin form submissions, cross-origin rejection, real client IP handling, dynamic prices, QR destinations and security headers, then smoke-test sign-in, customer upload/checkout/tracking, shop printing and subscription screens. Test the Dropbox Chooser if configured. The production CSP allows inline scripts/styles for Next.js and should be tightened further with nonces; its Dropbox/Supabase allowlist may need review for custom service domains. These checks are not a penetration test.

### Production rollout of `0010`

Use a planned maintenance window and a verified database backup. Stop new checkouts, apply `0010` transactionally, deploy the matching application, and verify customer checkout and shop payment confirmation before reopening. Do not leave the old code running against the new schema or deploy the new code against the old schema. Customers with pre-upgrade drafts must restart them; a customer who already sent a UPI payment should **not** pay again. If their old browser session cannot report the payment, the shop can find the order using its tracking link, record the customer's report, then independently verify and confirm the transfer.

## Subscriptions

Printly has **one all-features plan** with monthly, six-month and yearly terms. In **Admin → Subscription**, configure each price, Printly’s receiving UPI ID, the payee name and the in-app reminder window (1–30 days). Prices and recipient start unset: an unset price disables that term, and a request with a balance due requires both UPI details. An eligible fully discounted term can activate without UPI details. Prices are stored in paise; changes apply to new requests only. The recipient and price of an existing request are preserved. If another admin changes the plan while a settings form is open, saving is rejected; reload the saved values and review your edits rather than overwriting them.

The shop owner reviews a term in **Shop → Subscription** and may apply an eligible promo code. If a balance remains, the owner sends a one-time UPI transfer to Printly and submits its transaction reference. A report is **not** proof of payment and never activates access. In **Admin → Subscription**, independently check the actual receiving account, reference, amount and recipient before approving. If a valid code discounts the entire term to zero, confirming it activates that term immediately without a UPI payment or manual approval. A term is added after the end of any remaining entitlement, in calendar months using India time (Asia/Kolkata); rejected reports require a reason shown to the owner. Requests, decisions and permanent grants are recorded. There is no payment gateway, automatic payment verification, recurring charge or email/SMS reminder. Owners see an in-app warning and a once-per-session popup near expiry. If a transfer may have been sent but reporting fails, check the current request or contact Printly; do not pay twice.

Admins can create percentage or fixed-amount codes, choose eligible terms and dates, set optional total and per-shop limits, and publish linked announcements to shops and optionally the public pricing page. The shop screen separately displays term savings against the equivalent monthly cost, promo savings and the combined comparison. Existing requests keep their original price, recipient and any recorded offer; older requests do not acquire invented historical savings. See [subscription offer operations and rollout](docs/subscription-offers.md) for limits, safe retries and deployment guidance.

An admin may grant or revoke **permanent free access** for any shop without a purchase. This overrides but does not erase its paid or transition period; revoking it restores any remaining time. If permanent access is granted while a request is in progress, an owner who already paid can still submit the reference for review; otherwise they should cancel the unpaid request.

After expiry or when unsubscribed, the dashboard and ordinary shop-management APIs are locked, and the storefront will not accept new orders. **Shop → Open orders** remains available to staff for open jobs, customer UPI reports and looking up a specific previously placed order by tracking link. Transfers and refunds are handled separately; cancelling an order does not automatically refund it. Previously issued signed file URLs cannot be revoked until they expire. Historical commission/payout records are retained in the database for audit but their interfaces and new commission calculations have been removed; new checkout records zero commission.

### Production rollout of `0011`

Schedule a maintenance window, take and verify a backup, block access to older deployments and direct bypass paths, and allow in-flight checkout activity to finish. Apply `0011` and deploy the matching application as one coordinated cutover: the old app’s checkout snapshot is incompatible with the new database function, while the new app requires the new subscription tables. Do **not** deploy or roll back just one side. The migration grants every shop existing at that moment a one-time **30-day transition**, starting at migration time; shops created afterward have no free period. Do not reapply or reset it as a renewal mechanism.

Set the actual prices and receiving UPI details in the admin console; none are supplied by this repository. If the operator explicitly chooses to configure them after reopening, payment requests remain disabled, new shops cannot buy a term, and existing shops' 30-day transition is already counting down. Verify the transition rows, admin configuration, storefront availability, expiry lockout, existing-order recovery and a non-financial test of request/approval and permanent grant/revoke using an isolated test shop. Never mark a real payment approved without confirming its transfer. Make a coordinated rollback/recovery plan for both code and database before the cutover; do not discard historical payment data.

## Printly brand and QR artwork

The selected Printly logo is available in `public/brand/printly-logo-kit.zip`, including scalable SVGs and transparent PNGs for light and dark backgrounds. The website, browser icon, maintenance notice, order slip and QR artwork use the same mark. Newly generated shop QR codes and standees place a small white-backed mark in the code, use high error correction, and retain a four-module quiet zone. If a UPI payment QR would be too dense for a central logo, the mark is shown alongside the unobstructed code instead; the underlying payment link is unchanged.

Existing printed QR signs do not change automatically. Generate and print new QR codes or standees to use the new artwork; old codes keep their existing shop links. Always test the new print with the phones and printer in use.

## Shop QR standee

Open **Shop → Settings & QR → Create A4 standee**. The workspace uses the signed-in account's linked shop and its owner's saved profile; it does not create another shop or accept a shop ID from the browser. Generate again after editing saved details. If details change between preview and export, the export asks for a fresh preview. Shops with an active subscription can prepare a standee before approval, but customers cannot place orders until the shop is active and its subscription is current.

The standee QR opens `/s/p-<code>/order` for that shop. Set `NEXT_PUBLIC_SITE_URL` to the canonical site origin (no path, query, or credentials; HTTPS in production); the request's Host header is never used as a fallback. The existing simple QR in Settings remains available and points to the shop landing page. Standee responses are private and uncached.

The preview, one-page vector PDF, 300-dpi PNG and print view come from the same A4 artwork. The PDF embeds fonts for template text; shop and owner names are shaped as vector outlines for consistent complex-script rendering. Bundled fonts cover Latin, Arabic and Devanagari; unsupported characters or names that cannot fit produce a visible error instead of missing glyphs or clipping. Font licences are in `src/assets/standee-fonts/`.

Print on A4 portrait at actual size (100%), with browser headers and footers disabled. Always check the print preview and scan a paper copy with the phones and printer you plan to use. Automated tests decode both shops' generated PNGs and PDF rasters, including simulated grayscale, but do not substitute for physical Android/iPhone and paper tests.

## Access and shop identity

- Shop sign-in: `/login`. The public shop application is `/shop/signup`.
- Administrator sign-in: `/admin/login`. Admins manage applications in `/admin/shops`, separately from the shop workspace.
- Each shop has an immutable, unique public code. Customer links and QR codes use `/s/p-<code>`. Existing name-based links remain valid. The code is a public identifier, **not a password**: authenticated membership and database RLS protect private shop data.
- Names are compared without regard to case or repeated spaces. A unique name needs no name proof. An existing name requires a shop photo or a GSTIN in the correct format, and stays paused pending an administrator's review. A GSTIN format check does not establish ownership or registration. Photos are stored in the private `shop-name-proofs` bucket, accessible to administrators only. Owners can replace evidence in Settings if changes are requested.
- Demo credentials in the historical seed are publicly known and are suitable only for isolated development. Change a seeded admin password in **Admin → Settings** and a seeded shop password in **Shop → Settings & QR** before using a shared deployment. Provision real accounts before real-world use.
- The current shop application creates email-confirmed accounts without sending a verification email. This bypasses Supabase's email-confirmation setting; implement and configure verified-email onboarding (including production SMTP and redirect URLs) before relying on email address ownership or launching publicly. A lost signup response can mean the application was created despite an error: the UI advises signing in before retrying, and the server preserves potentially referenced proof/account records instead of deleting them. Operators should investigate `signup_unconfirmed` logs and reconcile any orphaned account or proof only after verifying that no application references them; there is no automatic orphan cleanup.
- Provider TOTP support does not by itself secure this portal: the app has no complete MFA enrollment/challenge flow or consistent AAL2 enforcement across APIs and RLS. Implement and test those controls before relying on MFA.

## Maintenance mode

In **Admin → Settings**, check **Enable maintenance mode** and select **Save settings**. Once saved, public/customer and shop pages return a self-contained maintenance page with HTTP 503, and their application APIs return a non-cacheable 503 error. The admin sign-in, console and admin APIs remain available and still require normal authorization; uncheck and save to reopen the site. Already-open pages check again while visible, about every 60 seconds and on focus, and display the notice without discarding their current input. Visitors who loaded the standalone maintenance page can use **Try again**. If the setting cannot be read, public requests fail closed with a generic unavailable message; the admin area remains accessible so the setting can be checked.

This is an application-level gate, not a database lock. Requests already in progress can finish, external UPI transfers cannot be stopped, and previously issued signed storage URLs or direct Supabase access are not revoked by the switch. Older deployments that do not contain this gate can also bypass it if their URLs remain accessible. For schema cutovers or sensitive maintenance, separately block old deployments and direct access as needed and allow in-flight work to finish before proceeding.

## Duplex printing and pricing

Customers may request double-sided printing or photocopying of each **whole file**; page ranges are not supported. Pages 1/2, 3/4 and so on occupy opposite sides. The back of an odd last page is blank, and every file and every copy starts on a fresh sheet.

In **Shop → Settings & QR → Rate card**, edit or add a print/photocopy row with sides set to Duplex. Choose **per printed page** or **per physical sheet** and explicitly set its price. Per-page quantity is document pages × copies, including any blank pages in the original document but not the additional odd-page reverse. Physical-sheet quantity is `ceil(pages / 2) × copies` for **each file**. For example, 5 pages × 2 copies uses 6 physical sheets; two separate one-page files × 2 copies use 4 sheets, not 2. The selected rate, quantity and line subtotal appear before checkout; rush, tax and add-ons are shown separately. Word counts are supplied by the customer and must be checked by the shop.

Existing prices and previously placed order totals are not changed. The historical `sheet` unit for print/photocopy/scan continues to be charged per document page; the new opt-in `duplex_sheet` unit is the only physical duplex-sheet rate. Lamination and other legacy rates keep their prior calculation. The most specific matching rate wins; configure the size, colour and GSM explicitly for predictable results. Equally specific overlapping physical-sheet rates are rejected when saving and fail closed when quoting until the ambiguity is resolved. Check the unit and price before saving. A price change during an uncommitted draft requires the customer to review the new quote; a checkout already started keeps its recorded amount.

The shop must select duplex and one page per side in the printer's dialog, check its flip edge, and inspect the output. Print one copy per job if the device cannot keep copies on separate sheets. The built-in raster print flow adds a blank final page for odd duplex files; browsers or drivers may suppress blank pages, so verify it. The native PDF viewer and downloaded/Word documents are unchanged and require the same manual checks. Printly cannot configure every printer or verify that printing succeeded.

### Production rollout of `0016`

Use a maintenance window, a verified backup and a coordinated app/database release. Allow in-flight checkout to finish, block old deployments and bypass paths, apply `0016`, then deploy the matching application before enabling physical-sheet rates. Confirm old rates and existing orders are unchanged, and test both pricing units, odd/even files and multiple copies using an isolated shop before reopening. Old app versions do not understand `duplex_sheet` and would quote it as pages × copies. The migration wraps checkout so an old engine cannot commit while a physical-sheet rate appears in its rate snapshot; the underlying transaction also rejects a stale snapshot. This safeguard does not correct an old quote or make old shop screens safe, so older deployments must remain blocked. The original checkout function is renamed and no longer executable by the service role; preserve that restriction. Do not roll back just the app or schema while physical-sheet rates exist; keep maintenance enabled and fix forward or plan a coordinated recovery that preserves shop rates and paid orders. Applying the migration itself does not change any rates.

## Customer previews and shop printing

- Customers can preview and crop/rotate individual PDF pages or JPEG/PNG images before checkout. Save replaces the file the shop receives; **PDF cropping is not redaction**: cropped-out PDF content can still exist in the file. Do not use it to hide confidential material. Image editing re-encodes the image. Reset restores the current page's unsaved edits; a saved edit cannot be undone unless the original is uploaded again.
- Files may be up to 25 MiB each, with at most 10 per order; images are limited to 40 megapixels and PDFs to 2,000 pages. Password-protected/unreadable PDFs must be unlocked or repaired before upload. PDF/image page counts are checked against the file. Word cannot be previewed or reliably counted here: customers must enter the page count from Word, and the shop should confirm layout and price before printing.
- New device uploads use signed TUS transfers with byte progress, automatic retries and same-tab resume. Keep the tab open: closing/reloading loses the in-memory file, signed token and resumable URL; it does not restore the draft. Tokens expire (normally after two hours), and incomplete TUS uploads expire (up to 24 hours). If a transfer cannot resume, remove it and add the file again; unfinished uploads may leave temporary/orphaned storage objects. Verification is a separate idempotent step and checkout remains disabled until every file is verified. Hosted Supabase uses the project's direct `*.storage.supabase.co` endpoint. An isolated rehearsal ran a production-mode app in Chromium against hosted staging: a 6,356,992-byte synthetic PDF survived a forced interruption and same-upload resume, matched its downloaded bytes, and passed CSP/CORS, upload gating, duplex cash checkout and tracking checks. Both staging and production Storage gateways also passed read-only origin preflights. This did not test a production upload, token expiry, lost creation responses or the delayed-upload/cancellation race; validate those and the target gateway credentials and proxy behavior before relying on them. Browser edits still use the existing standard signed-upload path.
- Removing a draft file detaches it and its linked draft items and attempts to delete its storage object. Failed cleanup is recorded for retry, but storage and the database are separate: a delayed signed upload can still leave an orphan after cleanup. Draft operations and previews require a 24-hour, order-scoped, HttpOnly cookie; a tracking link alone does not grant file access. Starting checkout locks file/option edits. Existing drafts created before this change have no draft cookie and must be restarted; placed orders and tracking links are unaffected. Expired drafts also need to be restarted.
- The shop's **Preview & print** shows the file and its linked customer settings. The browser/OS print dialog supplies printer selection and print preview; the operator must check paper size, copies, colour, sides and physical output. The dialog cannot prove a print succeeded. The optional physical-print check is local to that visit and does not change order status. For PDFs up to 20 pages the no-download print flow prepares raster pages at up to 144 dpi; for finer detail or longer documents, open the PDF in a compatible browser viewer or download it. Browser and printer support varies, especially on mobile; verify with the actual device.
- Order files are stored in a private Supabase bucket. An automatic draft/30-day file purge and automatic orphan-cleanup job are **not implemented** in this repository; configure and verify retention and orphan cleanup before promising automatic deletion to customers.
- The tracking page is the source of order updates. The application does not currently send automatic status notifications or email receipts; customers should save their tracking link. From the original browser, they can also report an already-sent UPI payment on that page while their draft session is valid. If their session has expired, the shop can find the order by tracking link and record the customer's report; this is not payment confirmation, and staff must still verify the transfer separately.

## Reliability, payment recovery and support

- Shop boards use server-side name, phone, token and UTR search, 30-order pagination per lane and exact counts. Opt-in audio is best-effort, needs browser permission and an open board, and is not a guaranteed notification. A failed refresh retains the previous snapshot and warns it may be stale. Visible tracking pages refresh about every 30 seconds, or 60 seconds when the browser reports data-saving/2G; background tabs pause and terminal orders stop periodic polling. Customers can refresh manually.
- Customer UPI reports and transaction references are **not** payment proof. Staff must independently check the receiving account, amount and reference. On confirmation, Printly warns if a normalized reference appears on another order in the same shop; staff can explicitly acknowledge the possible duplicate after checking. No reference, different spellings, late reports or transfers outside Printly can evade this advisory check. It is not a bank integration, a guarantee that a payment is unique, or automatic refund processing. Customers should check their UPI app and contact the shop before paying again.
- Customers and shop owners can write at `/support`; platform administrators read and reply under **Admin → Support**. A conversation's 256-bit access code is shown to the customer and is not stored by the app; save it privately because anyone with it can read/reply and a lost code cannot be recovered. Only its hash is stored server-side. The customer must return with the code to check replies; no email, SMS or push notification is sent. Messages are capped at 100 per conversation and may contain sensitive information, so restrict admin access and establish retention/deletion and operational response procedures. Closing does not delete a conversation; a customer reply reopens it. No support AI is included.
- English, Hindi and Urdu guidance is available on the core customer order, payment, tracking and support screens. Some advanced options, server errors and other pages remain English. The chosen language is saved as a non-sensitive browser preference when storage is available; Urdu screens use right-to-left layout. Review translations with native speakers before relying on them.

### Rollout of `0018`–`0020`

Do not apply these migrations to production or a preview sharing production until a restorable database **and Storage-object** backup, an isolated test environment and a coordinated release/rollback plan are verified. Take a maintenance window, drain in-flight work, block old deployment/bypass paths, rehearse the exact migrations and indexes on representative data, and apply them in order before deploying the matching code. `0018` replaces the limiter function and creates a board index; `0019` adds private support tables and service-role-only RPCs; `0020` adds a reference index and checked payment RPC. The new app depends on these RPCs. Preserve existing orders, messages, ACLs and payment events during recovery; rolling back only code or schema can strand support conversations or payment recovery. Test the signed TUS gateway with a non-sensitive file in the isolated environment before deployment, then verify private support authorization/retries, payment-warning flows with synthetic data, and actual printer behavior after release. These checks and the optional `pnpm test:reliability-concurrency` test are not a capacity/load guarantee.

The concurrency test creates and removes its own temporary PostgreSQL cluster over a private Unix socket; it never connects to an existing database. It requires `initdb`, `postgres`, `psql` and `stdbuf`, and must run as a non-root user. Set `PRINTLY_PG_BIN` if the PostgreSQL tools are not found through `pg_config`.

## Session behavior

Supabase's cookie-backed session persists across ordinary browser restarts and refreshes while valid. Signed-in linked shop staff visiting the homepage, shop sign-in, or shop application are directed to their workspace; customer shop links and tracking remain public. Private browsing, cleared/blocked cookies, explicit sign-out, revoked/expired refresh tokens or server-side session policies can still require sign-in. Sign out on shared devices. The sign-out button requests `local` scope so other devices are not signed out; if server revocation cannot be confirmed it warns rather than claiming success. Supabase access tokens already issued can remain valid until expiry even after a successful sign-out; protect shared devices and revoke sessions through the provider when necessary.
