# Printly for Shops — native Android (in progress)

This is a Kotlin/Jetpack Compose Android application. It is not a Trusted Web Activity, browser wrapper, or WebView. The matching gateway is deployed on the live site, but the native APK is **not yet a published production release**. The operator reports a successful partial isolated phone rehearsal; the signed production APK still needs verification and a device test.

## Build variants

- `debug`: package `io.github.dawartariq.printly.owner.native.debug`, labelled **Printly Native Demo**. It uses synthetic in-memory data, has no Firebase implementation, cannot access a real shop, and can be installed alongside the existing app. The demo is not a release and must not be used to make payments.
- `qa`: package `io.github.dawartariq.printly.owner.native.qa`, labelled **Printly Isolated Test** and signed with a disposable debug key. It uses live network calls but is pinned to the dedicated test website and staging Auth host, and uses the separate `printly-notifications-qa` Firebase client. It is for synthetic accounts only; never distribute it to owners or use real shop data. A website hostname alone does not prove its server backend is isolated.
- `release`: package `io.github.dawartariq.printly.owner`, local candidate version code 5/name 2.1.0 (the earlier review was code 4/name 2.0.1). It is configured for `https://printly0.vercel.app`, the production authentication project and the separate `printly-5c247` Firebase client. The operator reports no existing non-test installations. Use the verified release key and retain it securely for future updates; do not distribute a build signed with a disposable key. The signing guard requires `PRINTLY_ANDROID_KEYSTORE_PATH`, `PRINTLY_ANDROID_KEYSTORE_PASSWORD`, `PRINTLY_ANDROID_KEY_ALIAS`, `PRINTLY_ANDROID_KEY_PASSWORD`, and optionally `PRINTLY_ANDROID_KEYSTORE_TYPE` (`JKS` or `PKCS12`). Never commit credentials or keys.

With JDK 17 and Android SDK 36 installed:

```sh
cd apps/printly-owner-native-android
./gradlew testDebugUnitTest assembleDebug
./gradlew connectedDebugAndroidTest  # offline synthetic-data emulator
# Only after the dedicated test website's server environment is verified:
./gradlew assembleQa -PprintlyQaSiteOrigin=https://printly-native-test.vercel.app
```

QA refuses every other website origin and requires a matching QA Firebase client file. It checks the Auth host returned by the website against the staging project (`rahfmpsdbwbktlobntkm.supabase.co`) before sign-in. This is not a substitute for verifying the website's server-side environment or for reviewing staging data. The QA build does not launch a UPI app; use synthetic references and never send real money. This is not a payment sandbox. The debug signing identity and separate package cannot establish compatibility with an installed production APK; a new debug key may require replacing only a previous QA installation.

The native CI workflow builds and tests the demo and isolated QA variants, inspects their manifests and Firebase resources, tests the unsigned-release guard, and verifies the review signing path with a temporary CI-only key. A separately requested isolated 2.1.0 phone-test APK was built with real Gradle/SDK tooling; its checksum and test-server limitations are recorded in `docs/native-order-notifications.md`. The user reports that it installs, signs in and works for ordinary use on a phone; v2 notification and update flows have not been tested end to end. The [Android CI run](https://github.com/dawar-tariq/Printly-/actions/runs/45828701172) passed its offline Android 12 update-policy and QA tap tests, but its Android 13+ first-open permission test stopped at the offline safety guard because the emulator still reported an active network. That permission test remains outstanding. Both emulator scripts require `PRINTLY_DISPOSABLE_EMULATOR=1`, exactly one verified emulator and the primary user; they disable Wi-Fi and mobile data and uninstall its isolated QA package. Use a disposable CI AVD, never a personal emulator or phone. The checks reject currently connected extra devices, but cannot prevent another device from attaching later. This normal workflow uploads **no APKs**. Earlier, the user confirmed sign-in, notification opt-in and display of one synthetic **v1** test alert on Android 10; that does not validate the new v2 features. No real signing secrets or live customer data are used in this workflow. The separate protected native review workflow and the direct-download release gates are described in `docs/native-direct-distribution.md`.

## Current functionality

The native screens cover a branded system splash, sign-in and encrypted local sessions, an order board with search, advisory Supabase Realtime updates and foreground polling, order details and private file opening, explicit UPI payment review, order transitions, inventory, reports, shop profile and service settings, availability, existing rate prices, shop QR/standee sharing, subscription quotes/payment reports, and expired-shop order recovery. System share sheets and third-party document/UPI apps are launched only for those specific operations; no web content is embedded. See `docs/native-performance-and-updates.md` for Realtime prerequisites, optional Redis, customer contact privacy and the limited server-driven presentation settings.

Important limits:

- Adding/removing rates or changing their dimensions is not implemented in the native app. Existing prices can be changed one at a time with a value-based server-side comparison; inventory changes also compare the displayed values. These checks cannot detect an ABA change (a value changed and later changed back). Use a separately supported management channel for other rate edits until an atomic compare-and-replace backend is available.
- Profile and availability writes use the existing server's last-write-wins behavior and services can be partially saved; coordinate edits across devices. After an uncertain change, refresh and check the saved values before trying again. Inventory creation has no idempotency key: check the current list before adding again. The app refuses to show a truncated inventory and currently cannot load more than 1,000 items.
- Native account signup, password changes, forgotten-password recovery and in-app printing are not implemented. On Android 13+, the push-capable variants request the system notification permission once on first open; this does not enroll a device in FCM. Opt-in push notifications remain a candidate deployed only to isolated staging. One supervised synthetic QA alert was accepted by FCM and the user confirmed it appeared on the phone; no recurring scheduler is installed. See `docs/native-order-notifications.md`. Realtime is advisory, depends on the deployed publication and RLS, and works only while the Home or Orders screen is foregrounded; polling remains the fallback. Opening or sharing an order file delegates to another installed app.
- Server-delivered notice text, the home subtitle and a bounded board refresh interval can change without reinstalling this app after the matching backend is deployed. Other native behavior, layout, permissions and security fixes still require a properly signed binary update.
- Reports include currently confirmed/collected orders **created** during the selected India-time period, not payments by payment date, and do not deduct refunds. The native backend refuses to return an incomplete report over 1,000 orders; choose a shorter period. It is not an accounting ledger.
- Payment and subscription actions require operator review. A reported transfer is not proof of payment; a duplicate reference needs a separate deliberate acknowledgement. A subscription request key is stored before the write and reused after an uncertain result. Review request history and do not pay again when a response is uncertain.
- On-device sessions use Android Keystore AES-GCM, with backup and cleartext traffic disabled. Files shared with a viewer are cached privately and granted access via an unexported `FileProvider`; another app can retain its own copy after the owner opens/shares it.

## Backend candidate and release boundary

The matching candidate consists of `src/lib/api.ts`, `src/lib/native-session.ts`, `src/lib/native-me.ts`, `src/lib/native-order.ts`, `src/lib/native-inventory.ts`, `src/lib/native-recovery.ts`, `src/lib/native-rate-card.ts`, `src/lib/native-reports.ts`, `src/lib/shop-report-period.ts`, and the routes under `src/app/api/native/v1/`, plus their tests. The gateway allowlists methods and paths, verifies each bearer token with Supabase Auth, and delegates to existing shop membership, entitlement and mutation checks. It does not put the service-role key in the app. The baseline gateway works with the production schema through 0021; the Realtime and native order push candidates require migrations 0025 and 0026. The managed-notification/update candidate additionally requires 0027 and an ordered server rollout. Staging has already recorded 0025, 0026, its alignment fix and 0027; do not reapply them. The matching server is deployed only to isolated QA with delivery paused, and 0027 has not been applied to production. See `docs/native-notification-management.md` and `docs/native-order-notifications.md` for separate approval and migration gates.

Do not deploy a dirty working tree. This repository also contains unrelated deferred changes and migrations. The live gateway was deployed from the explicit clean web candidate, not those deferred files. Maintenance applies to the native gateway too. The operator reports restore-tested database and Storage backups; these were not independently inspected. See `docs/native-direct-distribution.md` for release and rollback limits, including the older website's lack of a native gateway.
